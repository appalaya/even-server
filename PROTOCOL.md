# Even Sync Protocol — v1

This is the complete contract between an Even client and an Even sync server.
Anyone can implement a server from this document alone. A server that passes
the conformance suite in `conformance/` is an Even server.

The server is deliberately ignorant. It stores opaque, client-encrypted events
per group, hands them back in order, and knows nothing about expenses, members,
names, amounts, or currencies. Everything in this document that concerns the
*contents* of an event is the client's business and lives in the client's own
documentation.

## 1. Terms

| Term | Meaning |
|---|---|
| **Secret** | 32 random bytes generated by the client that creates a group. The only credential. Travels in the invite. |
| **Server origin** | The canonical form of a server URL (§8.1). Part of key derivation, so tokens are per server. |
| **Auth token** | Derived from the secret **and the server origin**. Sent as a bearer token. Different for every server. |
| **Encryption key** | Derived from the secret. Never leaves the client. Same on every server. |
| **Group id** | SHA-256 of the auth token. Public identifier in URLs. Per server. Proves nothing on its own. |
| **Event** | One immutable, client-encrypted record. The unit of storage and sync. |
| **Envelope** | The unencrypted wrapper around an event: id, version, nonce, ciphertext. The only thing the server sees. |
| **Sequence (`seq`)** | A per-group integer the server assigns on accept, strictly increasing from 1 within an epoch. The sync cursor. |
| **Epoch** | A random value the server assigns when a group is (re)created. Changes whenever the group's storage is deleted and recreated. |
| **Invite** | A string carrying the server URL, the secret, and a checksum. Delivered as a link or pasted as a code. |

All byte-to-text encoding in this protocol is **base64url without padding**
(RFC 4648 §5). All strings fed to hash and key-derivation functions are UTF-8.

## 2. Key derivation

Given `secret` (32 bytes) and `origin` (the canonical server origin, §8.1):

```
encryptionKey = HKDF-SHA256(ikm = secret, salt = "even/v1", info = "enc",            length = 32)
localId       = base64url( HKDF-SHA256(ikm = secret, salt = "even/v1", info = "local", length = 32) )
authToken     =            HKDF-SHA256(ikm = secret, salt = "even/v1", info = "auth|" + origin, length = 32)
groupId       = base64url( SHA-256(authToken) )                                     // 43 characters
```

- `encryptionKey` and `localId` do not depend on the server. `localId` is how a
  client recognises "this invite is for a group I already have" regardless of
  which server the invite names.
- `authToken` and therefore `groupId` are **per server**. A token presented to
  one server is useless at any other. An operator the group once synced through
  cannot delete or write to the group on a different server.

The server receives only `authToken` (in the header) and `groupId` (in the URL).
It verifies membership by recomputing `base64url(SHA-256(authToken))` and
comparing it to the path's `groupId`. The server stores neither value ahead of
time and keeps no password table. The token is 256 random bits, so plain
SHA-256 is sufficient; no password hashing is needed or wanted. Constant-time
comparison is harmless but not required, since the comparand is a public hash.

The server never receives `secret`, `encryptionKey`, or `localId`. A correct
server implementation has no code path that could learn them.

## 3. Encryption

Clients encrypt each event body with **XChaCha20-Poly1305** (IETF, 24-byte
nonce).

```
plain      = UTF-8(JSON body)
padded     = plain || 0x80 || 0x00 × k      // k chosen so that len(padded) + 16 is a multiple of 256
nonce      = 24 random bytes, fresh per event, fresh again on any re-encryption
aad        = UTF-8( "even/v1|" + groupId + "|" + v + "|" + id )
ciphertext = XChaCha20-Poly1305.seal(key = encryptionKey, nonce, padded, aad)
```

- **Padding** (ISO/IEC 7816-4 style) hides exact plaintext length. The
  ciphertext (padded length plus the 16-byte tag) is always a multiple of 256,
  so the server learns only a 256-byte size class. Conforming clients
  therefore produce ciphertexts of 256, 512, …, 8192 bytes; the maximum padded
  length is 8176 and the maximum plaintext is 8175. Clients check the
  plaintext length before sealing and refuse to create an event that would
  not fit. On open, the client strips trailing zeros and the single `0x80`.
  The server's structural floor of 17 bytes (§4) is deliberately looser than
  what conforming clients produce.
- **Associated data** binds the protocol version, the group id, the envelope
  version `v` (as its decimal string), and the envelope id. A ciphertext cannot
  be replayed into another group, under another id, or relabelled as another
  envelope version, even by the server.
- Because `groupId` is per server, **re-encryption is required when a group is
  moved or copied to another server** (§8.3). Event ids and bodies are
  preserved; only nonce and ciphertext change.

Servers do not, and cannot, verify any of this; it is documented so that
independent clients interoperate.

## 4. Envelope

```json
{
  "id": "Q2bYbA1t6Gq9pD7Zk0xM3w",
  "v": 1,
  "n": "z9Nq4y…(32 chars)…",
  "c": "…base64url ciphertext…"
}
```

| Field | Type | Rule |
|---|---|---|
| `id` | string | base64url of 16 **random** bytes: exactly 22 characters, charset `[A-Za-z0-9_-]`. Not time-ordered, on purpose. Unique within a group; duplicates are ignored on write. |
| `v` | integer | Envelope version, a **positive** integer (JSON number with no fractional part). This document defines `1`. Anything that is not a positive integer (`0`, negatives, fractions, strings, booleans) is a structural error (`invalid_envelope`); a positive integer the server does not support is `unsupported_version`. |
| `n` | string | base64url of the 24-byte nonce: exactly 32 characters. |
| `c` | string | base64url ciphertext. Decoded length at least 17 and at most `max_event_bytes` (default 8192). |

No other fields are permitted. Servers reject envelopes with extra fields,
missing fields, wrong types, or malformed encodings with `invalid_envelope`.

**Stored size** of an envelope, for cap accounting, is the decoded byte length
of `c` plus 64. Servers use this definition so that published caps mean the
same thing everywhere.

When the server returns an envelope it adds two fields:

| Field | Type | Rule |
|---|---|---|
| `seq` | integer | Server-assigned, per group, strictly increasing from 1 within an epoch, never reused within an epoch. |
| `received_at` | integer | When this server first stored the envelope in the current epoch, in Unix milliseconds (UTC). It is assigned once, together with `seq`, and never changed afterwards, including by a duplicate write. Every envelope stored by one request gets the same value, and it is greater than the value of every envelope stored by an earlier request to the group. |

## 5. Transport rules

- HTTPS is mandatory. Clients refuse `http://` server URLs and refuse
  self-signed certificates. The one exception is a development build of the
  client reaching a server on the same machine or its private network
  (loopback, 10/8, 172.16/12, 192.168/16) over plain `http://`, for the
  reference server during development; keys are still derived from the
  `https` form of the URL, and a release build has no such exception. For
  anything else use a tunnel or a real certificate.
- Requests and responses are `application/json; charset=utf-8`.
- Authentication: `Authorization: Bearer <authToken base64url>` on every
  group-scoped request.
- Servers MUST return `Cache-Control: no-store` on all responses.
- Servers MAY support CORS for browser-based tooling. Native clients do not need it.

## 6. Endpoints

All paths are relative to the server URL carried in the invite (§8.1).
Example: `https://sync.even.appalaya.com`.

### 6.1 `GET /v1/info` — server capabilities (no auth)

```json
{
  "protocol": [1],
  "limits": {
    "max_event_bytes": 8192,
    "max_group_bytes": 2097152,
    "max_group_events": 10000,
    "max_batch": 25,
    "max_page": 500,
    "daily_write_budget": 0,
    "rate": {
      "requests_per_minute": 120,
      "writes_per_minute": 60,
      "group_creates_per_minute": 3,
      "reads_per_minute": 720
    }
  },
  "retention_days": 365,
  "push": false,
  "operator": "Even (appalaya.com)",
  "terms": "https://even.appalaya.com/terms"
}
```

Every limit the server enforces appears here, including `daily_write_budget`
(`0` means none; see §7 `over_budget`). With conforming clients the byte cap
already bounds a group to about 6,500 minimum-size events; `max_group_events`
exists to bound non-conforming clients that send tiny ciphertexts.
Servers MUST build this response from the same values the caps are enforced
with, so the two cannot drift. Clients call this when a group
is created or joined, cache it, refresh it on any `invalid_request`, and use it
to show the server's name, limits, and retention in group settings. `operator`
and `terms` are optional strings; `push` states whether §6.5 is implemented.
Rate limits are per client IP and may be enforced approximately.
`rate.reads_per_minute` is optional. It limits event reads (§6.3) on their
own; a server that does not limit them separately of other requests leaves it
out, and clients that do not know it ignore it (§11). A server MAY count a read
by its size, as one read for every started 100 rows it reads from its
database, so that a read returning few events counts once and a full page
counts several times; it then says so in its documentation. The reference
servers do: a read of up to 86 events, one with nothing new included, counts
once, and a full page of 500 counts six times. Clients honour `Retry-After`
(§10) and need not compute the count.

### 6.2 `POST /v1/groups/{groupId}/events` — append events

Request body:

```json
{ "events": [ <envelope>, <envelope>, … ] }
```

- 1 to `max_batch` envelopes per request.
- The group is created implicitly on its first successful write, receiving a
  fresh `epoch`. There is no create call.
- Validation order: request shape (`invalid_request`), then each envelope in
  array order. The first structurally invalid envelope → `400 invalid_envelope`
  with its `index`; an envelope that is well-formed but has an unsupported `v`
  → `415 unsupported_version` with its `index`. Structural errors take
  precedence when both occur in one batch. If **any** envelope is rejected the
  whole request is rejected and nothing is stored.
- Envelopes whose `id` already exists in the group are ignored and counted as
  duplicates. Their stored content is never replaced. An id repeated within one
  request is stored once.
- Accepted envelopes receive consecutive `seq` values in request order. The
  assignment MUST be atomic per request: two concurrent requests never
  interleave their sequences and never produce gaps or duplicates.
- Accepting the batch MUST NOT push the group past `max_group_bytes` (sum of
  stored sizes, §4) or `max_group_events`. If it would, reject the whole
  request with `413 group_full` and nothing is stored. Duplicates do not count
  toward either cap.

Response `200`:

```json
{ "accepted": 3, "duplicates": 1, "seq": 42, "epoch": "k3Jd…(22 chars)…", "received_at": [ … ] }
```

`seq` is the group's highest sequence after the write. `epoch` is the group's
current epoch (§6.6). `received_at` holds one value per envelope in the
request, in request order: the value stored for that id, which for a duplicate
is the one assigned when it was first stored. A `200` acknowledges **every**
envelope in the request, accepted or duplicate: the client may treat all of
them as stored.

### 6.3 `GET /v1/groups/{groupId}/events?since={seq}&limit={n}` — read events

- `since` defaults to `0`. Returns envelopes with `seq > since`, ascending.
- `limit` defaults to `max_page`; values above `max_page` are clamped; values
  below 1 → `400 invalid_request`.
- A group that does not exist returns `200` with an empty list, `"next"` equal
  to `since`, `"more": false`, and `"epoch": null`. Existence must not be
  distinguishable without a valid token, and an empty group and a missing
  group are the same thing to a client.

Response `200`:

```json
{
  "events": [ { "seq": 41, "id": "…", "v": 1, "n": "…", "c": "…", "received_at": 1790985600000 }, … ],
  "next": 41,
  "more": false,
  "epoch": "k3Jd…"
}
```

`next` is the `seq` of the last returned envelope, or `since` if none.
`more` is `true` if events with `seq > next` exist. Clients loop on `more`,
never on the count returned versus the count requested.

### 6.4 `DELETE /v1/groups/{groupId}` — delete the server copy

Deletes every event in the group and the group itself. Returns `204`.
Idempotent; deleting a missing group is `204`. Any holder of the secret may do
this. A subsequent write recreates the group with a **new epoch** and `seq`
restarting at 1. Every member keeps a full local copy, so this is a cache
purge, not a data loss; see §10 for how clients recover.

### 6.5 `PUT /v1/groups/{groupId}/subscriptions` — push subscriptions (reserved)

Reserved for a future protocol revision that lets a device register a push
token for a group. Servers that do not implement it MUST authenticate the
request as usual and then return `501 not_implemented`, and MUST report
`"push": false` in `/v1/info`. The v1 client
never calls it. It is listed so that adding push later is an additive change,
not a protocol bump.

### 6.6 Epochs

The server assigns a random 16-byte `epoch` (22 chars base64url) when a group
is created or recreated. It is returned on every read and write. Two
incarnations of the same group id never share an epoch. `seq` values are
meaningful only together with the epoch they were issued in.

## 7. Errors

All errors are JSON:

```json
{ "error": "group_full", "message": "optional human-readable detail" }
```

| Status | `error` | When |
|---|---|---|
| 400 | `invalid_request` | Body is not the documented shape, batch is empty or exceeds `max_batch`, bad query params, malformed `groupId` in the path. |
| 400 | `invalid_envelope` | An envelope fails §4. MUST include `"index"` of the first offender. |
| 401 | `unauthorized` | Missing or malformed bearer token, or its hash does not match `groupId`. Because auth is stateless, a correct client never receives this for a group it created or joined: it indicates a client bug, a proxy stripping headers, or an invite whose secret was mistyped. It never means "revoked". |
| 404 | `not_found` | Unknown route. |
| 405 | `method_not_allowed` | Known route, wrong method. |
| 413 | `group_full` | Write would exceed `max_group_bytes` or `max_group_events`. MAY include `"reason": "bytes" \| "events"`. |
| 415 | `unsupported_version` | An envelope's `v` is not supported by this server. MUST include `"index"`. |
| 410 | `group_blocked` | The operator has blocked this group id (takedown). Terminal: clients stop syncing the group through this server and never self-heal it there. |
| 429 | `rate_limited` | Per-IP limits exceeded. Include `Retry-After`. |
| 503 | `over_budget` | The operator's global write budget for the day is exhausted. Include `Retry-After`. Reads still work. |
| 5xx | `server_error` | Anything else. Clients retry with backoff. |

Clients treat `group_blocked` as terminal for that group on that server,
`group_full` as a hard stop that needs user attention,
`unsupported_version` as "this server needs updating", `invalid_request` as
"refresh `/v1/info` and re-batch", `invalid_envelope` as "quarantine that
envelope", and 429, 503, 5xx, and network failures as transient.

`GET /` and `GET /robots.txt` are outside the protocol: a server MAY answer
them with plain text for people and crawlers, or treat them as unknown
routes. §5's `Cache-Control: no-store` still applies to every response.
Clients never request them.

## 8. Invites

### 8.1 Server URL canonical form

The invite's `s` field, the `origin` used in §2, and the client's per-server
cursor all use the same canonical string:

- scheme `https` only, lowercase
- host lowercase, ASCII only (an internationalised name is written in its
  punycode form; clients reject non-ASCII hosts rather than converting)
- no userinfo, no default port (`:443` removed), other ports kept
- optional path, with no trailing slash, no query, no fragment
- Examples: `https://sync.even.appalaya.com`, `https://home.example.net:8443/even`

Two server URLs are the same server if and only if their canonical strings are
equal.

### 8.2 Payload

An invite is a JSON payload, base64url-encoded:

```json
{
  "v": 1,
  "s": "https://sync.even.appalaya.com",
  "k": "<secret base64url, 43 chars>",
  "h": "<first 4 bytes of SHA-256(secret bytes), base64url, 6 chars>",
  "g": "Banff 2026",
  "cur": "CAD"
}
```

| Field | Rule |
|---|---|
| `v` | Invite format version, `1`. |
| `s` | Canonical server URL (§8.1). |
| `k` | The group secret. |
| `h` | Checksum. Clients MUST reject an invite whose `h` does not match `k`. Protects against a mistyped or truncated code silently creating an empty group. |
| `g` | Optional group name, so the join screen can say what is being joined before any sync. |
| `cur` | Optional ISO 4217 currency code, so the join screen can format money before any sync. |

It travels two ways, and both carry the identical payload:

- **Link:** `https://even.appalaya.com/i#<payload>`. The payload is in the URL
  fragment, which browsers never send to the landing-page host. Universal links
  and App Links preserve fragments.
- **Code:** the bare `<payload>` string, for pasting into the app when a link
  cannot be delivered (fresh install, no deep-link association, desktop chat).

The payload MUST NOT be placed in a custom-scheme URL such as `even://…`, since
any installed app can claim a custom scheme.

### 8.3 Same group, different servers

Because `localId` is server-independent, a client that receives an invite for
a group it already holds, but with a different `s`, treats it as **"this group
now syncs through that server"**: it re-derives the token and group id for the
new origin, resets its cursor to 0, and pushes its full log there
(re-encrypted for the new group id, §3). This is how a group survives a dead
server: any member issues a fresh invite naming a new server.

### 8.4 Rotation and closure

To revoke access, a client generates a new secret, which yields a new
`localId`, a new encryption key, and new server ids. It re-encrypts its full
local log under the new key, **preserving every envelope id and body**, pushes
it to the chosen server, and issues a new invite. It does **not** delete the
old group on the old server; instead it writes one final event there whose
decrypted meaning is "this group is closed, ask a member for the new invite",
so that members who have not yet received the new invite stop and know why.
The old copy expires under the server's normal retention. The mechanics of
that event, and of how a member links the old and new groups locally, are the
client's concern.

## 9. Server obligations

- **Ordering.** `seq` is the only ordering the server provides. `received_at`
  is the server's clock, not an ordering; clients use it as an upper bound on
  the time an event claims.
- **Clock.** `received_at` comes from a clock kept within a minute of UTC. A
  server whose clock is wrong by more than a day makes clients hold back every
  write until the clock is corrected.
- **Epochs.** Assigned on creation and recreation, returned on every response
  for the group, never reused.
- **Retention.** A server MAY delete groups with no successful write for
  `retention_days`. It MUST publish that number in `/v1/info`.
- **Limits.** Every limit the server enforces MUST appear in `/v1/info` and
  MUST be enforced as published.
- **Rate limiting.** Servers SHOULD limit, per client IP: total requests,
  write requests, and group creations, and MAY also limit event reads,
  counted by size if they choose (published as the optional
  `rate.reads_per_minute`, §6.1). Servers SHOULD key IPv6 clients by /64.
  Operators should expect a whole group behind one NAT to share a bucket.
- **Blocking.** Servers MAY keep a blocklist of group ids and answer every
  request for a blocked id with `410 group_blocked`. This is the takedown
  mechanism; a plain delete is undone by the next member who syncs.
- **Logging.** Servers MUST NOT log request bodies or bearer tokens, and MUST
  NOT write request URLs (which contain group ids) to persistent logs. Platform
  access logs that cannot be disabled MUST be disclosed in `terms`.
- **No fingerprinting.** Servers MUST NOT require any client attestation,
  app-specific header, or API key beyond the bearer token. Any client that
  speaks this protocol is a valid client.

## 10. Client obligations

- Push the outbox before pulling, so a device's own events are never fetched
  back as "new" before they are acknowledged.
- Store the cursor **and the epoch** per group per canonical server URL.
- Store each envelope's `received_at` with its `seq`. Replace it with the value
  in every push and pull response, and clear it whenever the cursor is reset
  (an epoch change or a server change). Never send it to a server.
- When no epoch is stored yet, adopt the first non-null epoch seen without
  resetting anything. When a response carries a non-null epoch that differs
  from the stored one, or `null` where one is stored: store the new value, set
  the cursor to 0, and mark every local event as unacknowledged, so the full
  log is pushed again. This is the self-heal path for expiry, accidental
  deletion, and server replacement; duplicate handling makes it safe. Compare
  the epoch **before** committing a pulled page. Allow at most one such reset
  per sync cycle; a second change within one cycle means the server is
  unstable, and the client stops syncing that group and says so.
- Never self-heal a group the user has closed, hidden, or left, or one the
  server answered `410 group_blocked` for.
- Loop on `more`, not on returned count. Commit each pulled page and its cursor
  update in one local transaction. Honour `Retry-After` on 429 and 503.
- On `invalid_envelope`, quarantine the envelope at `index` so it is never
  resent, and continue with the rest. On `invalid_request`, refresh `/v1/info`
  and re-batch. On repeated 5xx for the same batch, halve the batch size before
  retrying. Treat `404`/`405` on a documented route as "this URL is not an Even
  server".
- Treat an envelope that fails to decrypt, or whose decrypted body fails
  validation, as skipped: count it, show the count, never crash. Keep
  envelopes with an unknown `v` or an unknown body version, since a future
  client may read them. Envelopes that fail authentication under the correct
  key are junk and MAY be discarded after a bounded number are kept.
- Never send an `http://` request (outside the development-build exception
  in §5), never disable certificate validation.

## 11. Versioning

- The path prefix `/v1` and the envelope field `v` are independent. The path
  versions the HTTP surface; the envelope versions the wrapper. Both change
  rarely and only for breaking changes.
- The **contents** of an event are versioned inside the ciphertext by the
  client, invisible to the server. Clients can change what an expense looks
  like without any server anywhere being upgraded.
- Additive fields in responses and additive endpoints (such as §6.5) are not a
  version bump. Clients MUST ignore response fields they do not know, including
  fields inside each envelope of a page.

## 12. Conformance

`conformance/` contains an executable test suite that runs against any server
URL. Passing it is the definition of an Even server. It covers every MUST in
this document, including atomic sequencing under concurrent writes, duplicate
handling within and across requests, whole-batch rejection with `index`,
precedence of 400 over 415, `more` and clamping semantics, epoch change after
delete, cap enforcement with duplicates exempt, `410` for a blocked id,
authentication before `501`, and the missing-group-is-empty rule. For
`received_at` it asserts that every envelope on every pulled page carries one, a
safe integer within 5 minutes of the runner's clock when the envelope was
appended; that the push response holds one value per envelope in request order,
a duplicate (within the request or stored earlier) reporting the stored value;
that the values are stable across re-reads and duplicate re-pushes; that they
are equal within one request and strictly increasing across requests in `seq`
order, concurrent requests included; that after a delete and recreate every
value is new and no earlier than the recreate time; and that push and pull
report the same value for an id.

Cap tests require small caps. The full suite MUST be run against an instance
configured with `max_group_bytes ≤ 65536` and `max_group_events ≤ 200`; the
suite refuses to report success against a server whose published caps are
larger than that, and says so. Operators of public servers run the suite
against a staging deployment with test limits.
